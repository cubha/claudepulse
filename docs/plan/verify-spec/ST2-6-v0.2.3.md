## A5 — 확장 소유 Codex 버킷 이력 (Phase 3 FIX, scope-critic 수용)

**변경**: `src/extension.ts` · `src/messaging/contracts.ts`(+`GetCodexPollHistory`) · `src/messaging/handlers.ts` · `src/webview/codexBucketHistory.ts`(+와이어 변환기) · `panelView.ts` · `sidebarView.ts` · `test/unit/codexBucketHistory.test.ts`(+4건)

- 지적 (scope-critic, `DECISION_CHANGED: yes`)
  - `panelCodexHistory`(패널)와 `sbCodexHistory`(사이드바)가 **별도 Map**이라, 열린 시점이 다른 만큼 쌓인 포인트 수가 다르다. `calcBurnRate`는 30분 안정화 구간의 가장 오래된 점을 기준으로 잡으므로 → **같은 버킷의 소모율이 두 화면에서 다르게 보인다.**
  - 실제 시나리오: 사이드바는 확장 활성화 때 열리고, 대시보드는 사용자가 나중에 연다. `retainContextWhenHidden: true`가 걸려 있어 세션 내 파기는 없지만, **출발 시각 자체가 다르다.**
- 처분: **수용하고 고쳤다.** Claude가 이미 같은 문제를 푼 구조를 그대로 따랐다 — `extension.ts`의 `snapshotHistory` + `GetPollHistory` pre-hydrate.
  - 확장이 `codexBucketHistory: Map<number, PollPoint[]>`를 소유하고 `doRefreshCodexUsage()`에서 누적
  - `GetCodexPollHistory` 요청 신설. Map·Date는 직렬화를 통과하지 못하므로 평탄 배열(`CodexBucketHistoryPoint[]`, `t`는 ISO 문자열)로 보낸다 — Claude의 `PollHistoryPoint`가 `t: string`인 것과 같은 이유
  - 웹뷰 양쪽이 init에서 받아 `hydrateCodexBucketHistory()`로 병합
- 구현 결정
  - hydrate는 **통째 교체가 아니라 시각 순 병합**이다. 요청을 보낸 뒤 응답 전에 브로드캐스트를 먼저 받는 순서가 실제로 가능하고, 그때 갈아치우면 방금 받은 최신 점이 사라진다. 같은 `(버킷, 시각)`은 중복으로 쌓지 않는다.
  - 웹뷰는 hydrate 후에도 push를 로컬 누적한다 — 두 화면이 같은 브로드캐스트를 동시에 받으므로 정렬이 유지된다.
- 게이트: 단위 4건(왕복 동일성 · **경쟁 상황** · 중복 방지 · 상한). hydrate를 통째 교체로 되돌려 RED 확인.
- 미확인 사항
  - 확장 재시작 시 `codexBucketHistory`는 비어서 시작한다(Claude의 `snapshotHistory`도 동일). 영속화는 범위 밖.
  - 두 웹뷰가 **동시에** 열려 있을 때 브로드캐스트 전달 순서가 어긋나는 경우는 재현하지 못했다. 같은 `generatedAt`이면 hydrate의 중복 방지가 잡지만, push 경로(`appendCodexBucketHistory`)에는 그 방지가 없다 — 다만 push는 양쪽에 동일하게 가므로 **정렬은 깨지지 않는다**(중복이 생겨도 양쪽에 똑같이 생긴다).
