## 구현 결정
1. **메타데이터(`ino`/`birthtimeMs`)가 아니라 내용 지문.** WSL/DrvFs ↔ 네이티브 Windows에서 그 값들의 의미가 달라, 비교가 틀리면 폴링(15s)마다 전체 재파싱이 도는 쪽으로 조용히 무너진다 — 원래 버그보다 나쁜 결과.
2. **base64 아니라 hex + 상호 접두 비교.** rollout은 append-only라 파일이 256B 미만인 동안에만 지문 길이가 자란다. hex는 바이트 접두가 곧 문자열 접두라 그 구간에서 거짓 불일치가 안 난다(base64는 패딩 때문에 이 성질이 없다).
3. **지문 읽기 실패는 증분 포기**(전체 재파싱). 이어지는 `readFileChunk`가 같은 실패를 로깅하므로 무성 실패가 아니다.
4. ST8 예산: PLAN §3에서 "~10줄+테스트 1 초과 시 이월"로 잡았으나 **캐시가 둘이라 두 호출 지점에 각각 배선**해야 해 실제 ~20줄이 됐다. 기계적 반복이고 재설계가 아니라 진행했다 — **초과 사실을 여기 명시**한다.

## 미확인 사항
- **ST8 성능**: 파일마다 refresh당 `open/read(256B)/close`가 1회 추가된다. rollout 파일 수가 수백 개인 홈에서 실측하지 않았다 — 256바이트라 I/O보다 syscall 오버헤드가 지배적일 텐데, 현재 코드가 이미 파일마다 `stat`을 부르므로 상대 증가는 2배 수준으로 추정(측정 아님).
- **실제 rotate 시나리오는 합성 재현**이다. Codex CLI가 rollout 파일을 같은 경로에 같은 크기로 교체하는 실사례는 관측된 적이 없다(가능성에 대한 방어). 테스트는 `fs.writeFileSync`로 인위 재현했다.
- ST6의 `root` lazy화가 **panelView.ts 쪽에는 적용되지 않았다** — 같은 패턴(`panelView.ts`도 모듈 최상단 `root`)이 남아 있어 그 파일은 여전히 node env import 불가. 이번 요구사항에 필요하지 않아 손대지 않았다(범위 밖). `panelDesign.invariants.test.ts`는 소스를 **텍스트로 읽어** 검증하므로 영향 없음.
